Getting started

Crabcrop is one Rust binary. Install it, give it a secret, and request images with the operations written into the URL. There are no pre-generated thumbnails and no build step: the URL is the API.

Install

# Shell installer (macOS and Linux)
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/dayvson/crabcrop/releases/latest/download/crabcrop-installer.sh | sh

# Docker: the base image, and the AI variant
docker pull ghcr.io/dayvson/crabcrop:0.11.0
docker pull ghcr.io/dayvson/crabcrop-ai:0.11.0

The AI variant ships only the background removal (u2netp) and face detection (YuNet) models. Every other AI feature needs its own model configured, and answers 501 without one; see AI operations.

Prebuilt tarballs for macOS and Linux, on x86_64 and arm64, are on the releases page.

Building from source instead (cargo run, cargo build, or cargo install crabcrop) needs a C compiler and, on x86_64, nasm. Meson and ninja are needed only for the vendored AVIF decode route.

Quickstart

# 1. Start the server with a new secret. Unsafe is for local dev only.
export CRABCROP_SECRET="$(openssl rand -hex 16)"
CRABCROP_ALLOW_UNSAFE=1 crabcrop
# crabcrop listening on port 3000

# 2. Request an image: resize a source photo to 300x200.
curl "http://localhost:3000/unsafe/300x200/https://example.com/photo.jpg" --output photo.jpg

# 3. In production, drop CRABCROP_ALLOW_UNSAFE and sign the URL instead.
#    In a shell with the same CRABCROP_SECRET, crabcrop sign prints the signed URL.
curl "$(crabcrop sign 300x200/https://example.com/photo.jpg)" --output photo.jpg

Every image request has three parts: GET /<signature>/<operations>/<source-url>. Operations apply in path order. Requested outputs are capped at 16383 px per axis and 100 megapixels in total, and so is every size a step works out along the way; a request past either bound fails with 400 before anything is allocated. The image the server encodes is held to the same cap, so a source with a 16384 px side needs a step that brings it within. A factor from the DPR client hint is the exception: it steps down to the largest factor that fits instead of failing. A request also runs at most 100 operations, counted after preset: references expand and with the server's default operations merged in, each filter in a filters: segment once; a request over the cap answers 400 (unsupported_operation) right after parsing, before any source fetch. A URL whose own operations already pass the cap is refused before its presets expand, and preset references may expand to at most 256 KiB of text.

Signing

Compute HMAC-SHA256 over the remainder of the path, the operations and the source URL exactly as they appear, with no leading slash, keyed with your CRABCROP_SECRET, and hex-encode the result as the first path segment. A request with a bad signature gets 403 and the body bad signature. The literal signature unsafe skips verification only when the server runs with CRABCROP_ALLOW_UNSAFE=1. Keep it off in production.

printf '%s' '300x200/https://example.com/photo.jpg' \
  | openssl dgst -sha256 -hmac 'your-secret'

import { buildURL, buildSrcSet } from "@crabcrop/url";

const base = "https://img.example.com";
const secret = "your-secret"; // read it from the environment in real code
const source = "https://example.com/photo.jpg";

// buildURL(base, secret, operations, source, { expires?, keyId? })
const url = buildURL(base, secret, "300x200", source);

// buildSrcSet(base, secret, source, widths): one {width}x0 URL per width
const srcset = buildSrcSet(base, secret, source, [400, 800, 1200]);
from crabcrop_url import build_url, build_srcset

base = "https://img.example.com"
secret = "your-secret"  # read it from the environment in real code
source = "https://example.com/photo.jpg"

# build_url(base, secret, operations, source, expires=None, key_id=None)
url = build_url(base, secret, "300x200", source)

# build_srcset(base, secret, source, widths): one {width}x0 URL per width
srcset = build_srcset(base, secret, source, [400, 800, 1200])
use crabcrop_url::{build_srcset, build_url, sign};

let base = "https://img.example.com";
let secret: &[u8] = b"your-secret"; // read it from the environment in real code
let source = "https://example.com/photo.jpg";

// sign(secret, remainder): the hex tag the curl tab prints, or an error for a reserved remainder
let signature = sign(secret, "300x200/https://example.com/photo.jpg")?;

// build_url(base, secret, operations, source, expires); a None secret builds the unsafe form
let url = build_url(base, Some(secret), "300x200", source, None)?;

// build_srcset(base, secret, source, widths, expires): one {width}x0 URL per width
let srcset = build_srcset(base, Some(secret), source, &[400, 800, 1200], None)?;

Every tab signs the same example, the second test vector below, so each one mints the same URL. The builders take positional arguments in the same order in all three languages: base, secret, operations, source. A null secret in TypeScript (None in Python and Rust) builds the unsafe form. The expiry comes last: an options object in TypeScript, a keyword argument in Python, a fifth argument in Rust. The Rust builders return a Result, and so does sign since 0.11.0, so the Rust tab runs inside a function that returns one and uses ?; code that called sign before 0.11.0 now unwraps the result. A srcset entry is a bare {width}x0 resize; to keep a preset or a format in every entry, build each width with the URL builder instead.

Secret your-secret, remainder 300x200/https://example.com/photo.jpg, HMAC-SHA256 3c1f6c180116661877bd4c85fd201a178087d74c1cc188cc584e819d901308c6. Every SDK runs the canonical vectors from spec/test-vectors.json as its test suite, so client and server cannot drift.

The reserved segment

The first segment crabcrop is reserved. The keys the server derives from the secret (for purges, uploads, sealed URLs, and its stored cache entries) are HMACs of labels such as crabcrop/purge-key, so a signature over one of those labels would be that key. Since 0.11.0 no first-party signer signs a remainder that is crabcrop or begins with crabcrop/, and the server answers one with 400 (reserved_segment) before it looks at the signature. It names no source the server could fetch, so no working URL is affected, and existing signatures stay valid. If you write your own signer, refuse it too: Reserved remainders in the spec has the rule and the test vectors.

Key IDs and rotation

A signature segment may carry a key ID, <key-id>:<tag>. During a rotation window the server verifies both the current secret (CRABCROP_SECRET) and the outgoing one (CRABCROP_SECRET_PREVIOUS), so URLs already in the wild keep working until the old key's URLs age out. An unknown key ID is indistinguishable from a bad signature: 403, with no hint about which IDs exist. Builders stamp the ID with keyId / key_id options, or crabcrop sign --key-id on the CLI.

Sealed URLs

Signing proves a URL was minted by someone holding the secret, but it hides nothing: the operations and the source sit in the path for anyone to read. A sealed URL encrypts that whole remainder into an opaque token that takes the signature's place: s1. followed by base64url of the nonce, the ciphertext, and the authentication tag, sealed with AES-256-GCM under a key derived from the same CRABCROP_SECRET. There is no second secret to manage, and key rotation works exactly as it does for signatures, key IDs included. Mint one with the CLI (crabcrop seal) or the seal builders in the Rust, TypeScript, and Python SDKs; Python sealing needs the crabcrop-url[seal] extra.

The payload is the whole remainder, operations and source together, so a sealed URL serves exactly what its plain spelling serves: the server opens the token and runs the same pipeline, and both spellings share one cache entry, one ETag, and one purge target. Everything after the token is a friendly name, purely cosmetic, there so the link still reads as an image in logs and page source; it is never parsed, and it may be left off entirely. Minting refuses a remainder longer than 2,048 bytes, and the server refuses a token longer than 4,096 characters.

Every sealed failure answers the same 403 with the body bad signature: a malformed token, a token minted under another secret, and a token whose payload does not parse are indistinguishable from each other. The one exception is a token that opens but has expired, which answers signature expired, exactly like the plain form. /explain refuses sealed URLs rather than decrypt them: a server endpoint that opens tokens would hand anyone who lifts one off a public page a way to read it. To debug a sealed link, unseal it locally under your own secret (crabcrop unseal, or the unseal builders in the SDKs) and explain the plain form. The meta document for a sealed request likewise reports the render, never the recipe.

Know what sealing does not do. It hides the recipe from page readers, the visitors and competitors who can see the link; anyone who can observe the request itself, like a CDN or another network intermediary, still sees it go by, and transport privacy is what TLS is for. It is not access control: a sealed URL is a bearer URL that anyone can replay, exactly like a signed one, and authorization stays with the source allowlist, expiry, and whatever fronts the deployment. For most links the readable form is the better default, and it stays the recommendation; sealing is the opt-in for links that must be public and unreadable at the same time.

URL anatomy and expiry

Click a segment. The strip is the whole grammar at a glance: one signature, zero or more operation segments, then the source, which starts at the first segment that is not an operation and may itself contain slashes.

https://img.example.com/////
Signature. Proof the URL came from you. The server recomputes the HMAC-SHA256 over the operations and source exactly as they appear. A match serves the image; a miss gets a 403.

Expiring URLs

Add an exp:<unix-seconds> segment anywhere among the operations. It is inside the signed remainder, so the HMAC covers it: extending the expiry without the secret breaks the signature. The URL is valid strictly before its exp second, with no clock skew allowance. Past it, the request gets 403 with the body signature expired, and expired URLs never serve from cache. URLs without exp: never expire.

/<signature>/exp:1893456000/300x200/https://example.com/photo.jpg

Per-request cache lifetime

Image responses normally carry Cache-Control: public, max-age=31536000, immutable, because a signed URL's bytes never change. Since 0.11.0 a response a client hint applies to carries private with the same lifetime instead, so only the browser that asked keeps it (see Client hints and Save-Data). A maxage:<seconds> segment (0 to 31536000) overrides the max-age for that response only. It changes the header, never the cache key, so URLs differing only in maxage share one stored image. maxage:0 drops immutable: caches must revalidate, and every cacheable response carries a strong ETag so revalidation can answer 304 Not Modified.

A size written in the URL is at most 16383 px per axis: 16384x100 does not parse and fails with 400 (invalid_size). The same limit holds for every size the server works out along the way (a proportional or orig side, a fit-in scale, a crop or pad target, any of these scaled by dpr or a DPR hint, and the larger canvas of a rotate(...)), and each step's output is held to 100 megapixels. A step past either bound fails the whole request with 400 (unsupported_operation) before it allocates, and the size is never clamped: 16383x1/0x2 asks for 32766x2 and is refused, while 5461x1/0x3 renders 16383x3. With no_upscale the cap shrinks a resize, fit-in, or crop first and the limit applies to what is left; a pad canvas is never shrunk. A factor that comes only from a DPR client hint is the exception: it steps down to the largest one that fits, and the request renders (see Client hints).

A source can decode at up to 16384 px per axis, one past the limit. The image the server encodes is held to the limit too, whatever the chain did: a chain that leaves a side past 16383 px, such as a 16384 px source with no sizing step or no operations at all, fails with 400 (unsupported_operation) in every output format, with a message that asks for a resize or crop. A chain that brings the side within the limit renders as before. Before 0.10.1, WebP output of such a source failed with 500 and every other format served 16384 px.

Fit inside a box

fit-in:<width>x<height>[:adaptive] scales proportionally so the image fits inside the box. A 0 axis is unbounded; a zero written with more digits (fit-in:00x100) is a zero-pixel side and fails with 400, as it does for a resize. Flips are not allowed here. With :adaptive, the box axes swap when the source orientation disagrees with the box's, so a portrait photo in a landscape box is not squeezed by the tighter axis.

Pad to an exact size

pad:<width>x<height>[:<fill>] fits inside the box, centers the image, and fills the rest of the canvas so the output is exactly the requested size. The fill is a 6-digit hex color, or blur for ambient bars made from a cover-scaled, heavily blurred copy of the image itself. Both dimensions are required: a 0 axis, orig, and flips are rejected.

Crop to an aspect ratio

crop:<width>x<height>[:<align>] crops to the width:height aspect ratio, then resizes to exactly that size. Align picks what survives: center (the default), top, bottom, left, right, the four corners (each keeps that corner's edges on whichever axis is cut), smart (a window on the focal point: a detected face when a face model is configured, otherwise the point of greatest local detail; the window shifts to keep detected faces whole), face (a window around the largest detected face, padded by facepad; falls back to the smart window when no face is found), and objects(<class>[,<class>...])[:<scale>].

The objects form crops to what a detection model finds: a window around the union of every detected object of the named classes, so crop:800x800:objects(dog) frames the dog and crop:1200x630:objects(person,car):1.5 frames every person and car with margin. Classes are the class filters' vocabulary, matched ASCII case-insensitively (Person repeats person, but É and é are two classes), up to 32 distinct names; a 33rd is a 400 (invalid_crop). The window is the smallest region of the requested aspect that holds the union box scaled by <scale> about its center (default 1, the tight box; above 1 adds margin, below 1 tightens), clamped into the frame. It needs CRABCROP_DETECT_MODEL: with no model the URL answers 501, never a silent plain crop, and a class outside the model's vocabulary is a 400. When the model runs and finds none of the classes, or detection fails, the crop falls back to center. Meta reports the decision under objects_crop, and debug:focal draws the detections and the union box.

Crop a rectangle, focal rectangle, focal point, debug view

crop-rect:<left>x<top>:<right>x<bottom> cuts the exact pixel rectangle between two corners, in the pixels of the image as it stands at the segment (the source, when nothing runs before it); a rectangle outside that image fails with 400, it is not clamped. A focal: segment in the same form names the rectangle the next crop: must keep: center and smart crops position their window on it, and a smart crop with one pending skips detection entirely. The steps between a focal segment and its crop carry the focal form with the image: a resize or fit-in scales it, a resize flip mirrors it, a crop-rect or trim cuts it, and a pad moves it onto the canvas, while a filter that moves pixels another way (rotate, flip, upscale, studio) drops it and the crop falls back to its own alignment. A focalpoint: segment names the point the next crop: centers on instead, as fractions of the image dimensions with an optional zoom: focalpoint:<x>x<y>[:<zoom>], so focalpoint:0.75x0.4:2 is three quarters across and two fifths down, at zoom 2. Center and smart crops position on the point; the directional alignments and face ignore it, and when a URL carries both focal forms, the last one before the crop wins. At zoom 1 the crop is the ordinary fill crop positioned on the point; above 1 the window tightens around the point, and below 1 it loosens toward the fill window, which it can never exceed. The zoom runs from above 0 to 100 and defaults to 1. Because the point is fractional it addresses whatever image is in effect at that point in the chain and can never fall outside it, so there is no bounds failure: this is the form imgix focal-point crops (fp-x, fp-y, fp-z) migrate to, with the fractions and the zoom carried over as written. The coordinates as written are not scaled by dpr. debug:focal renders a diagnostic image instead of the result, with the chosen focal point, face boxes, and crop window drawn on it; debug responses are never cached.

curl "http://localhost:3000/unsafe/crop:1200x630:top/https://example.com/photo.jpg"
curl "http://localhost:3000/unsafe/crop-rect:100x50:700x450/https://example.com/photo.jpg"
curl "http://localhost:3000/unsafe/focal:100x50:700x450/crop:800x600:smart/https://example.com/photo.jpg"
curl "http://localhost:3000/unsafe/focalpoint:0.75x0.4:2/crop:800x600/https://example.com/photo.jpg"
curl "http://localhost:3000/unsafe/crop:800x800:objects(dog):1.5/https://example.com/pets.jpg"

Overlays and text

Three filters composite onto the image. Overlay images are fetched through the same loader, limits, and source policy as source images, each with a fetch budget of its own, and a failed overlay fails the request with 502 (or 400 invalid_source when its URL is not one the server can fetch at all) instead of being skipped. These run on the server's pixels at the filter's position in the chain, so there is no honest browser stand-in: the examples below are the exact requests.

Watermark

filters:watermark(<url>,<x>,<y>,<alpha>). The URL is percent-encoded (it lives inside a path segment). Negative x and y anchor from the right and bottom edges. Alpha runs 0 (invisible) to 100 (opaque), and the watermark's own alpha is honored.

# Overlay a logo at the bottom right, 80% opaque
curl "http://localhost:3000/unsafe/filters:watermark(https%3A%2F%2Fcdn.example.com%2Flogo.png,-10,-10,80)/https://example.com/photo.jpg"

Overlay with blend modes

filters:overlay(<url>,<x>,<y>,<alpha>,<blend>[,<width>]) generalizes the watermark: blend is normal, multiply, screen, or overlay (the CSS formulas per channel), and the optional width scales the overlay to that percentage of the base image's width before compositing. The base image's alpha channel is preserved.

curl "http://localhost:3000/unsafe/filters:overlay(https%3A%2F%2Fcdn.example.com%2Ftexture.png,0,0,60,multiply,100)/https://example.com/photo.jpg"

Text

filters:text(<text>,<size>,<color>,<anchor>) draws a label with a font configured on the server (CRABCROP_FONT_PATH; with no font configured, text requests fail with 501). Size is 1 to 1000 px; color is rrggbb or rrggbbaa; anchor is one of nine grid points, from top-left to bottom-right. Put text after your resize so it draws sharp at the final resolution.

curl "http://localhost:3000/unsafe/800x600/filters:text(Sale%20ends%20soon,32,ffffff,bottom-right)/https://example.com/photo.jpg"

Encoder options

A format(...) directive takes its encoder's options after the format name. One format's options combine, each named at most once: format(jpeg,progressive,subsampling:444). A format named with no options renders byte for byte as it always has.

quality(auto), verified

quality(auto) picks a quality per image, from 50 for flat images to 95 for detailed ones. For JPEG and JPEG XL the pick is then verified: crabcrop encodes, decodes, and scores the result against the processed source with SSIMULACRA2, adjusting until it lands on target (75 by default), and reports the achieved score in meta. When crabcrop chooses the quality, the response carries an X-Crabcrop-Quality header with the value used.

Negotiation

When the URL names no format(...), the request's Accept header decides. Among AVIF, JPEG XL, and WebP, the highest q-value wins; ties break by server preference in that order; a format refused with q=0 is never picked; wildcards do not count as an offer. If none of the three is offered, the source format is kept. Animated sources never negotiate to JPEG XL, which would drop their frames.

Client hints and Save-Data

When a URL sizes nothing itself (no size, crop, fit-in, pad, or crop-rect), the server honors the width client hints, read in order: Sec-CH-Width, Width, Sec-CH-Viewport-Width, Viewport-Width. It resizes as if the URL carried a width-only size plus no_upscale, with the DPR hint multiplying on top under the same cap, so a hint never enlarges a raster source: on a 640×480 source, Sec-CH-Width: 3000 returns 640×480. An SVG source still renders at the hinted width, since a vector has no pixels to invent. Hinted widths round up to a multiple of CRABCROP_WIDTH_STEP (100 px by default) and stop at 3840, so nearby viewports share one cache entry and every hint past 3840 shares the 3840 entry. Image responses advertise Accept-CH for these hints and vary on them, unless CRABCROP_CLIENT_HINTS=0 turns hints off. The 3840 stop and the no-enlarge rule are new in 0.9.11; 0.9.10 resized to the hinted width as asked.

The Sec-CH-DPR and DPR hints scale every pixel size in a URL that carries no dpr(...), and take the same values: 1, 1.5, 2, or 3; any other value is ignored. Since 0.10.1 a DPR hint never fails a URL on the output limits. When the hinted factor alone would push a size past 16383 px on an axis or past 100 million pixels, the server serves the image at the largest of 1, 1.5, 2, and 3 that fits: /unsafe/6000x1/<source> with DPR: 3 serves 12000x2, where 0.10.0 answered 400. A hinted factor past 1 also never serves a side past 16383 px, so 8192x1 on a 16384x2 source with DPR: 2 serves 12288x2, at 1.5. If even factor 1 does not fit, the URL itself is over the limits and answers 400 under any hint. A stepped-down render is cached under the hinted factor, so it never answers the URL without the hint.

A request with Save-Data: on gets the default quality stepped down one notch, from 80 to 70, on the formats that carry a quality. A URL with any quality(...) in force (its own, a preset's, or the default operations') is unaffected, a per-format list included, even one with no value for the output format; before 0.11.0 such a list did not stop the step.

Since 0.11.0 a response any of these hints applies to is served Cache-Control: private instead of public, with the same lifetime: a width hint on a URL that sizes nothing itself, a DPR hint other than 1 on a URL with no dpr(...) in force, or Save-Data on a URL with no quality(...) in force. These are the cases that get their own cache entry. The browser that asked keeps the response, and a shared cache that keys on the URL alone stores only the URL's response without hints, which stays public. Whether a hint changed the bytes is known only after the render, so the response is private even when it matches that one byte for byte. CRABCROP_CLIENT_HINTS=0 switches all of these hints off: the server ignores the headers, every request for a URL gets the same bytes, responses vary on Accept alone, and no Accept-CH is sent. Set it behind a CDN that does not put these headers in its cache key (see Put a CDN in front).

Video output

An animated GIF or WebP can leave as real video: filters:format(mp4) or format(webm), the gifv pattern. Video frames

A video source can also be an image source: a frame: segment selects one frame, and that frame becomes the source image the rest of the URL operates on. It flows through crops (face-safe smart crops included), filters, studio mode, and format negotiation like any other source image. The selection applies at decode, wherever the segment sits in the path; when a URL carries several frame: segments, the last one wins.

frame:poster
frame:<seconds>
frame:<percent>%
curl "http://localhost:3000/unsafe/frame:50%/800x450/filters:format(webp)/https://example.com/clip.mp4"

frame:poster is the video's first frame, frame:1.5 is the frame at a timestamp in seconds, and frame:50% is the frame at a percentage of the duration. The edges:

  • Frame selection is video-only. A frame: segment on a still image or an animated GIF or WebP source fails with 502, the way a bad source fails; animated sources keep their existing behavior whenever no frame: segment is present.
  • Out-of-range selections clamp: a timestamp past the end of the video serves the last frame, and so does frame:100%. Nothing about the request is an error. A percentage needs the video's duration; a container that reports none fails the percentage form with 400.
  • A malformed selector (a sign, an exponent, a percentage over 100, a timestamp over 86400) fails with 400 and the invalid_frame code, before any fetch.

Extraction is an operator feature: crabcrop ships no video decoder. It runs through the external decoder configured with CRABCROP_VIDEO_DECODER (FFmpeg is the reference), validated at startup; with the variable unset, a frame: URL answers 501. Since 0.11.0 the decoder may open only the codecs common in video from the web, broadcast, phones, and cameras: H.264, HEVC, VP8, VP9, AV1, MPEG-4 Part 2, H.263, MPEG-1 and MPEG-2 video, Theora, Motion JPEG, ProRes, and DV. A stream in another codec, such as Windows Media video (WMV, VC-1), Sorenson H.263 or VP6 in FLV, or a lossless, raw, or screen-capture codec, yields no frame and answers 502; audio, subtitle, and data streams are left alone, so an MP4 with an AAC track extracts as before. Frames are held to the decode budget the extracted frame has to pass anyway, 16384 px on a side and 67108864 pixels, in every video stream. A stream's coded size, which can be larger than the picture it shows, may be 16384 px on a side and 68141056 pixels, room for the padding a codec adds to whole blocks. A larger frame or coded size answers 502, and 1080p H.264, coded 1920x1088, extracts as before. The decoder runs under a 3 GiB address-space cap. Since 0.11.0 crabcrop passes the decoder more of FFmpeg's options, among them -codec_whitelist, -max_pixels, and -threads, and runs the probe at -v verbose to read the coded size, so a program configured in place of FFmpeg must accept them. The video itself comes through the ordinary loader first, under the same fetch cap as any source (CRABCROP_SOURCE_MAX_MB, 10 MiB by default: raise it for longer clips) and the same fetch timeout. Extraction happens once per unique URL on a cache miss, and the result caches and purges like any other render. A frame render's meta response carries a video object: the stream's width and height, its duration in seconds when the container reports one, and the frame_timestamp the frame was selected at, after clamping. See Meta endpoint.

PDF pages

A PDF source can also be an image source: a page: segment selects one page, rendered as the source image the rest of the URL operates on. page:1 is the document's first page. The page renders its crop box, the area a PDF viewer shows, at a fixed scale of 2 (a 144 dpi raster), clamped down for very large pages so neither raster axis passes 16382 px and the raster stays within 64 megapixels. From there the request is an ordinary image request: crops, filters, studio mode, and format negotiation apply unchanged. One page per request: there are no ranges and no contact sheets. When a URL carries several page: segments, the last one wins.

page:<n>
curl "http://localhost:3000/unsafe/page:2/800x1000/filters:format(webp)/https://example.com/report.pdf"

The edges:

  • Page selection is PDF-only. A page: segment on an image, a video, or any other source fails with 502, the way a bad source fails.
  • Pages are 1-based and the number is exact: page:9 on a three-page document fails with 400. It never clamps to the last page, the deliberate difference from frame: timestamps: a frame is a position inside a stream, while a page is a numbered object a caller picks by identity, so a wrong number is a wrong request, not a position past the end.
  • The number is canonicalized: page:007 is page:7, and both spellings share one cache entry. A malformed selector (zero, a sign, letters, more than six digits) fails with 400 and the invalid_page code, before any fetch.
  • A document that needs a password to open fails with 400. A document that is merely permission-encrypted and opens without a password renders normally. Documents over 1000 pages are refused.
  • A page too large to fit the raster limits even at 1 dpi (over 16382 inches on a side, or over 64 million square inches) fails with 502 before the renderer runs.
  • The PDF tools run under a 3 GiB address-space cap since 0.11.0. An embedded image whose decode needs more than the cap is left out of the page, and a page whose own surfaces need more fails with 502. A document that stores a JPEG 2000 image too large for the cap (more than 201326592 pixels in RGB, where 16384x12288 fits, or 402653184 in gray) fails with 502 for every page, before either tool runs. Images within the cap, such as a 600 dpi A3 scan, render as before.

Rendering is an operator feature: crabcrop ships no PDF renderer. It runs through the external renderer configured with CRABCROP_PDF_RENDERER (Poppler's pdftocairo is the reference), validated at startup; crabcrop derives the pdfinfo program next to it, in the same directory, and uses it to probe documents. The renderer is run with -cropbox, so a program configured in place of pdftocairo must accept that flag; before 0.10.1 it drew the media box, which a page can declare much larger than its crop box. Each run is bounded by CRABCROP_PDF_TIMEOUT_SECS (default 30). With the variable unset, a page: URL answers 501. The document comes through the ordinary loader first, under the same fetch cap as any source (CRABCROP_SOURCE_MAX_MB, 10 MiB by default: raise it for larger documents). The tools receive only the document bytes over stdin, so external references, embedded files, and document actions or scripts have no target and no effect. A page render's meta response carries a pdf object: the document's pages count, the page rendered, and the page's page_width and page_height in points (its crop box, the area rendered). See Meta endpoint.

AI operations

AI filters run ONNX models you supply as files, loaded at boot before the server reports ready. Crabcrop never downloads a model. A configured model that cannot load is a startup error, not a surprise for the first request. With no model configured, the filter answers a clean 501, and nothing silently degrades: upscale never falls back to a plain resize, and a detection failure fails a redaction request rather than serving an unredacted image: 502 (inference_bad_output) when the model's output is unusable, 500 (inference_failed) for any other failure. Inference runs behind a server-wide gate of 2 concurrent inferences.

Region removal: remove_region

Point CRABCROP_INPAINT_MODEL at a LaMa family inpainting model and the remove_region(x,y,w,h) filter erases a rectangle and inpaints it from the surrounding pixels, with the same bounds rule as blur_region: a rectangle that overflows the image is a 400. Each removal runs the model once on a square crop window around the rectangle, and only the rectangle's pixels are taken from the result: everything outside it comes back bit-identical. The source's alpha and sample depth are kept, inside the rectangle too: transparent pixels stay transparent, and a 16-bit or float source is written back at its own precision. Before 0.10.1, remove_region and upscale served a 16-bit or float source as opaque 8-bit RGB. Meta responses for a removal carry an inpaint object listing the erased rectangles. Know the limit before you rely on it: the model fabricates what goes in the hole. The fill is plausible on smooth or textured surroundings and visibly wrong on structured content: text, faces, repeating patterns, straight edges that should continue. A removal takes seconds of inference behind the shared AI gate, and the result cache absorbs repeat requests for the same URL, so a given removal is normally paid for once.

Segmentation: class operations follow the silhouette

Point CRABCROP_SEGMENT_ENCODER_MODEL and CRABCROP_SEGMENT_DECODER_MODEL at a MobileSAM export pair (an image encoder and a box-prompt decoder; both are required together) and the class filters change shape: blurclass and pixelateclass redact each object's silhouette instead of its rectangle, and recolorclass paints the silhouette. Segmentation is box-prompted: each detection goes to the decoder as its own box, and the mask decides, pixel by pixel, what the operation touches; the mask's soft edge blends, so silhouettes antialias instead of stair-stepping. The image is encoded once per request however many class operations chain, and each box costs one small decode. Meta responses for a request that segmented carry a segments object: per object, the label, the detection score and box, the mask's tight box (the silhouette's own extent, often well inside the detection), its coverage (the share of the box the silhouette fills), and its centroid. Without the pair, the class filters keep their rectangle behavior exactly. With the pair, a segmentation failure fails the request like a detection failure does, never a silently rectangular redaction. Class operations still need a detection model: the segmenter refines boxes, it does not find them.

Scene mode: studio(scene)

studio(scene) is the second mode: it keeps the photograph's scene instead of cutting the subject out. One filter expands into a smart crop on the detected subject plus a per-image light and color correction, run at the filter's position in the chain. The same mask model runs first; without one configured, studio(scene) fails with 501, the same way. The subject is picked from the mask's connected regions at the subject threshold: the largest wins, ties break toward the frame center, then reading order. The frame is cropped to the smallest window with the frame's own aspect ratio that holds the subject with its pad margin, then resized back to the canvas in effect, so the output keeps the size the chain expects and later operations compose unchanged. The correction is driven by the reframed image's own histogram: a per-channel levels stretch between the 0.5th and 99.5th percentiles (a channel whose span is too flat to stretch is left alone), then a saturation factor that steers the image's mean saturation toward 0.30, capped at 1.35 and never below 1, so muted photographs gain color and vivid ones are never desaturated.

Scene takes one argument: pad, 0 to 40, default 10, the margin the subject keeps in the reframed window. The product arguments are bad arguments under scene: bg or shadow named with studio(scene) is a 400. If the mask finds no subject (or only a speck not worth believing), the fallback skips the crop and serves the original framing, corrected. Meta reports scene runs in the same studio field, with mode set to scene and a scene object: the winning subject's box (or null), how many candidate subjects the mask carried, the crop window applied, the per-channel levels stretch, and the saturation factor, alongside the steps and fallbacks.

# Reframe on the subject and correct, default pad
curl "http://localhost:3000/unsafe/filters:studio(scene)/https://example.com/shoe.jpg"
# A wider margin around the subject
curl "http://localhost:3000/unsafe/filters:studio(scene,pad:25)/https://example.com/shoe.jpg"

Presets

A preset names an operation string on the server, so URLs stay short and the transformation menu stays operator-controlled. Define presets in a file, one per line, and point CRABCROP_PRESETS_FILE at it:

# /etc/crabcrop/presets.txt
og-card = crop:1200x630:smart/filters:format(webp):quality(80)
thumb = 300x200
curl "http://localhost:3000/<signature>/preset:og-card/https://example.com/photo.jpg"

The signature covers the preset reference; the server expands it deterministically after verification, and cache entries key on the expanded operations. Treat a preset as a stable template: never edit a definition in place. Roll a change out under a new name (thumb2). Editing in place changes the bytes behind URLs already signed and shared, and image responses travel with an immutable cache header for a year, so downstream browsers and CDNs keep serving the old response beyond the reach of any purge. An unknown preset name is a 400. Definitions are validated at startup (blank lines and lines starting with # are skipped), and presets cannot contain a source segment, an exp:, a maxage:, another preset, more than the 100 operations a request may run, or more than the 256 KiB of text a request may expand to; any of these refuses the boot.

With CRABCROP_ONLY_PRESETS=1, free-form operations are rejected with 400: requests may use preset references, exp: and maxage: metadata, and bare sources only, and the rule applies to signed requests too. Combined with unsafe mode it makes a public deployment where browsers and CMSs build URLs from preset names alone, with no secret to hold. Clients still choose the source, so set CRABCROP_ALLOWED_SOURCES to the hosts your images come from: without it the server fetches from any public host, and every host name a request carries takes one of the source host lookup slots. Unsafe mode without presets-only is not a public mode: it honors any unsigned operation chain, so configured presets constrain nothing, and it is for local development only. See Framework loaders for which mode each integration fits. Responses for preset URLs carry a Cache-Group header naming the preset, which is what purge-group clears.

Source roots

A source root names an origin on the server, so a URL can carry a short source instead of spelling out the full source URL: the origin layout stays off the URL, and URLs get shorter. Define roots in a file, one per line, and point CRABCROP_SOURCE_ROOTS_FILE at it:

# /etc/crabcrop/roots.txt
photos = https://cdn.example.com/photos
media = https://assets.example.com
curl "http://localhost:3000/<signature>/300x200/root:photos/cat.jpg"

That request fetches https://cdn.example.com/photos/cat.jpg. The signature covers the short form exactly as written; the server expands it after verification and before cache keying, so the short spelling and the full URL it expands to are one render: they share a cache entry, and purging either spelling evicts it. Root definitions are validated at startup: names are letters, digits, _, or -, a duplicate name refuses the boot, and a base must be an absolute http(s) URL with no userinfo, query, or fragment.

The safety rules:

  • The source allowlist (CRABCROP_ALLOWED_SOURCES) and every other loader check apply to the expanded URL, exactly as if the client had spelled it out. A root never widens what the server will fetch.
  • The path must stay under the root. Dot segments are normalized, and a path that climbs above the root, plainly or percent-encoded, is a 400 (invalid_root).
  • An unknown root name is a 400 (unknown_root), including on a server with no roots configured.
  • Root base URLs are operator configuration and stay private: explain reports the source as written plus the root's name, and never prints a base URL.

Local filefile:///pathMust stay under CRABCROP_FILE_ROOT. A path with a .. segment is refused before the server touches the filesystem, and the rest are canonicalized per request, so a symlink cannot lead out of the root either. Since 0.11.0 every path refused this way, or that cannot be resolved inside the root, answers 404 (source_not_found), the answer a missing file gets, whatever exists at it. Unset root disables file sources.

A source in none of these forms is a 400 with the code invalid_source: text that does not parse as a URL, another scheme (ftp://, data:), or a malformed locator (s3:// with no bucket or key, a file path carrying a NUL). The fault is the URL's own, so it never reaches the network and never falls back to the fallback image. Watermark and overlay URLs and the /explain route answer the same. A redirect to such a URL is different: that is the origin's answer, and it fails as a source fetch (502). Before 0.10.0 these answered 502 source_fetch_failed.

Bucket sources are gated by CRABCROP_ALLOWED_BUCKETS rather than the host policy. When signing credentials are configured, the allowlist is required: the server refuses to boot without it, because signed fetches would otherwise reach every bucket the credentials can read. List * to deliberately allow all buckets. A bucket or object key carrying a dot segment, a path component that is exactly . or .., is refused, since the request path would collapse it past the allowlisted bucket; dots inside a segment name are fine. Bucket names must follow the S3 naming rules (3 to 63 characters of lowercase letters, digits, dots, and hyphens, starting and ending with a letter or digit, no adjacent dots, no dot beside a hyphen, not an IP address spelling): the name is interpolated into the request host, so a name carrying a host-breaking character is refused at parse time, whatever the allowlist says. Store responses are not redirected: a 3xx from a store surfaces as its status code.

Fetch and decode limits

  • 10 seconds per source fetch in total by default (CRABCROP_SOURCE_TIMEOUT_SECS, 1 to 600): one budget spans the whole redirect chain (up to 5 hops) and the body read, so a chain of fast hops cannot stretch a fetch past it. A fetch past it answers 504 (source_timeout). A fallback image fetched in the source's place and each watermark are separate fetches with a budget each, and the processing timeout starts only once they are done, so keep the sum under your proxy's or CDN's upstream timeout.
  • 10 MiB maximum body by default (CRABCROP_SOURCE_MAX_MB, 1 to 1024), for every source kind and type, watermarks included; larger sources fail with 502 (source_too_large). Raise it to serve frame: from longer clips or page: from larger PDFs.
  • Source bytes held in memory share one budget (CRABCROP_SOURCE_BUFFER_MAX_MB; by default four fetch caps per processing lane permit, so it grows with the cap). Every source, watermark, fallback, and upload body is charged as it arrives and stays charged until the render that uses it is done. A source reserves at most 1 MiB ahead of the bytes it has received, and the rest of its declared length only once it has received that much. It keeps budget past its received bytes only while it keeps up: at least 64 KiB each second, and enough to fill what it holds before the fetch timeout. A source that falls behind, whether its origin stalls or sends slowly, holds only what it sent. Before 0.10.1 a slow origin that sent a byte each second kept its whole declared length. A request that cannot get budget within 5 seconds sheds with 503 (server_busy) and Retry-After: 1. Boot prints a source fetch: line with the cap, the timeout, and the budget.
  • A Content-Type header, when present, must start with image/: the exceptions are a video/* source under a frame: segment (see Video frames) and an application/pdf source under a page: segment (see PDF pages).
  • Decoding is bounded: at most 16384 px per axis, 256 MiB of decoder allocations, and animated sources at most 200 frames, 100 million decoded pixels, and 256 MiB of decoded frames in total. Since 0.11.0 a GIF frame counts at the larger of the GIF's canvas and its own declared size, and a GIF's frames are counted from their headers before any of them decodes. Animated frames decode one at a time under the processing deadline, and decoding past it stops with 504. A JPEG XL frame may hold no more pixels than a whole image may, and a HEIC/HEIF file's item graph is bounded by the work it takes to walk and the memory the decode holds while it builds it (128 MiB), worked out from the item tables before the walk runs. Sources past any of these bounds fail with 502. An AVIF source's container is checked before it is parsed: a box that declares more bytes than the file holds fails with 502 before anything is set aside. Its item table is checked too: an item with too many extents, or extents that add up to more bytes than the file holds for it, and a primary image whose declared size is past the decode limits, each fail with 502 (415 as an upload) before any decoding.

What decodes

JPEG, PNG, WebP, GIF, JPEG XL, and TIFF sources are decoded. TIFF decoding is the pure-Rust tiff decoder under the same decode bounds as every other format; a multipage TIFF renders its first page, and a floating-point TIFF has its samples clamped to the 0 to 1 range and renders like a 16-bit source. EXIF orientation is applied before any operation runs, so phone photos come out upright. Animated GIFs keep their frames when the output format is GIF or WebP; converting an animated GIF to a still format uses the first frame. Animated WebPs keep their frames when the output format is WebP or GIF, with frame delays and the loop count preserved; converting one to a still format uses the first frame. Animated WebP output is encoded through libwebp at the request quality, the same mapping as still WebP: 80 by default, and quality(100) encodes losslessly. Every render that encodes animated WebP output (an animated WebP kept as WebP, or an animated GIF converted to WebP, named or negotiated) runs behind a dedicated gate of one encode at a time, on the slow lane: while one is running, another waits up to 10 seconds for the slot and then sheds with a 503 rather than queueing behind a long encode.

AVIF sources are decoded in builds that include AVIF decoding: the Docker image and the release binaries. A source build includes it with --features avif-decode, which links dav1d (a system libdav1d 1.3 or newer, or a vendored build); without it, AVIF sources fail with 502 and an error naming the feature. Animated AVIF sources decode their first frame. Since 0.10.1 the decode runs in the SVG worker process (see below): an AVIF still decoding at the processing deadline fails with 504, and one whose decode crashes or runs out of memory fails with 502, while the server carries on. Valid files decode to the same pixels as before. Upload validation, which has no request deadline, gives an AVIF decode 30 seconds. HEIC and HEIF sources are decoded in every build by the pure-Rust oxideav stack: the primary image only, with grid and overlay compositions resolved, EXIF orientation honored, and 10-bit sources flattened to the pipeline's 8-bit working space, as AVIF sources are. A HEIF file decodes only when every image it is built from is HEVC-coded; one that would need another codec (an AV1, H.264, or H.266 item behind a generic mif1 brand, say) fails with 502 before any decoding starts.

BMP and ICO sources are decoded too, under the same bounds; an ICO renders the image it carries with the deepest color, the largest if several tie. No other raster format is decoded: OpenEXR, Radiance HDR, QOI, PNM, DDS, TGA, and farbfeld sources fail with 502, and as uploads with 415.

SVG sources

SVG sources are supported and detected by content, not by the declared content type. An SVG is sanitized before it is rendered: script elements, event handlers, and references to external resources are stripped, so a source SVG can only draw what it carries with it. Since 0.11.0 an href is kept only when it names an element of the document (#id) or is a well-formed data: URL, and the renderer draws an image only from a data: payload the document embeds: it never reads a file an href names. What it carries is bounded before anything renders: at most 100,000 nodes once <use> references, patterns, masks, clip paths, markers, and filters are expanded, every embedded raster image counted against the 256 MiB decode budget once for each time it is drawn, references nested at most 128 levels deep, and no reference cycles. Both bounds are checked from the document's structure before the renderer builds anything, so a few kilobytes of references that would expand exponentially are refused in milliseconds; a document past any bound fails with 502. Since 0.10.1 that check bounds its own work too: it charges for every element it visits and every value it reads, and caps how much stylesheet matching it does, so a document that would make the check run longer than linear in its size is refused with 502 as well. Image requests, upload validation, and /explain all run it. SVG images nested in the document share its bounds, and a gzip-compressed (svgz) nested image is not drawn.

Each SVG is parsed and rendered in a separate worker process, never in the server itself: the server starts its own binary as a worker, which caps its own CPU time and, on Linux, its address space at 4 GiB, and is killed at the request's processing deadline. A worker that crashes or runs out of memory fails its own request with 502 (decode_failed), one still rendering at the deadline fails with 504 (processing_timeout), and the server carries on. Like any render, the worker's run holds a stills lane permit until it ends, and the stills lane has one permit per core, so on a one-core host a still render that misses the cache, or an upload, that arrives during a long SVG render waits up to 5 seconds and then answers 503 (server_busy). Health checks and cache hits do not wait. AVIF sources (renders, uploads, and watermark images) decode in the same worker, under the same limits and deadline. The worker reads documents up to 64 MiB. The sanitized document is rasterized at the size the URL asks for (or its intrinsic size when the URL asks for none), at most 4096 px per axis, and then runs through the normal pipeline. Output defaults to PNG for SVG sources.

Private address protection

CRABCROP_BLOCK_PRIVATE_SOURCES is on by default: the loader refuses sources whose host is, or resolves to, a non-public address: loopback, private, link-local, unspecified, shared (CGNAT), reserved, multicast, broadcast, documentation, benchmarking, and the other special-purpose ranges, including IPv4-mapped, IPv4-compatible, and 6to4 spellings of them, checked before connecting and again on every redirect hop. For a hostname, the loader resolves it, checks every address, and pins the connection to the validated address, so the address that was checked is the address that gets connected: a name that rebinds between the check and the connect cannot reach a private address. A refusal decided from the URL itself answers 403 (source_forbidden): a host off the allowlist, an IP address in a non-public range, or credentials in the URL. Since 0.11.0 a host name that resolves to a non-public address answers 502 (source_fetch_failed) instead, exactly as a name that does not resolve answers, with the fallback image in its place when one is configured, so the answer does not tell a client which names resolve inside the server's network. The server log names the cause. This holds on the image route, /explain, and watermarks, for the source and every redirect hop.

Source host lookups have slots of their own since 0.11.0: at most 128 run at once per server, covering this check's lookups and the HTTP client's own lookup for a fetch the check does not pin. A request that waits more than 5 seconds for a slot answers 503 (server_busy) with Retry-After, and never falls back. IP literals need no lookup, and the s3:// and gs:// endpoints resolve apart from the slots. A resolver that does not answer holds its slot until it gives up, so requests naming hosts whose DNS does not answer can keep the slots taken, and meanwhile other sources that need a lookup answer 503; cached results and sources that need no lookup keep working. Where clients choose the source host, as in presets-only public mode, set CRABCROP_ALLOWED_SOURCES: a host off the list is refused from its name alone, before any lookup. /metrics reports the slots in use as crabcrop_source_lookups_in_flight against crabcrop_source_lookups_capacity.

Two exceptions are deliberate, and both drop the pinning along with the check:

  • An allowlisted host is exempt. Listing a host in CRABCROP_ALLOWED_SOURCES is how a deployment vouches for a loopback or internal source, so a host that matches the allowlist is neither address-checked nor pinned, and its DNS may answer with any address, private ones included. The rebinding protection above covers only hosts off the allowlist. Allowlist only suffixes whose DNS you control: a suffix also matches every subdomain under it, and a subdomain whose DNS someone else controls can point at a private address.
  • The check can be switched off. CRABCROP_BLOCK_PRIVATE_SOURCES=0 turns it off, and so does CRABCROP_ALLOW_ANY_SOURCE=1, the deliberate opt-out, whatever the first is set to. With the check off, no source is address-checked or pinned; an allowlist, when one is set, still applies.

Pinned fetches connect directly and never go through a proxy: a proxy resolves the host again on its own, so it could connect to an address the check never saw. Every other fetch (allowlisted hosts, IP-literal sources, bucket sources, and every source when the check is off) honors HTTPS_PROXY, HTTP_PROXY, and ALL_PROXY, in either case. On a network whose only way out is a proxy, pinned fetches therefore fail, and with no allowlist every hostname source is pinned, so boot prints a warning when a proxy variable is set under that policy (it names the variables, never their values). To fetch through the proxy, list your source hosts in CRABCROP_ALLOWED_SOURCES: listed hosts are fetched unpinned, through the proxy, and every other host is refused. Listing a host also exempts it from the address check, so list only hosts you trust.

Fallback image

With CRABCROP_FALLBACK_IMAGE set, a source that cannot be fetched or decoded degrades to the fallback instead of an error: the fallback runs through the same operations and is served with 200 and the header X-Crabcrop-Fallback: 1. Signature and parse failures never fall back, a 400 or 403 stays honest, and neither does a source-policy refusal, a source URL the server cannot fetch at all (invalid_source), or a request shed with server_busy. Fallback responses are never cached and are served with Cache-Control: no-store, so a recovered origin is picked up on the next request and no intermediary pins the placeholder in place of the real image.

Meta endpoint

Send Accept: application/json with any image URL and get metadata about the processed image instead of the image bytes. Meta responses are served with Cache-Control: private, no-store and are never cached: a URL has two representations, and intermediaries must never pin one in place of the other.

Meta mode is off by default, since 0.10.0: turn it on with CRABCROP_META_MODE=1. While it is off, a meta request answers 403 with the code meta_disabled before any fetch or render, and the same URL without the header serves the image as usual. The refusal carries the meta document's Cache-Control: private, no-store and Vary headers, so a cache that honors them never serves it in place of the image. Know the cost before you turn it on: meta is the most expensive request a signed URL can trigger. It bypasses every cache tier, so each request fetches the source, renders it, and runs the configured annotation models again: CLIP tags and the aesthetic score on every request, the others when the request opts in, and any caller can opt in to all of them. Concurrent identical meta requests share one run; one after another, each pays in full. Any viewer of a signed URL can send the header, so enable meta only where you use it. 0.9.11 added the switch but left it on; when you upgrade, set it on any deployment that uses meta, the crabcrop meta verb, or the MCP server's fetch_meta tool. With meta mode on, boot prints meta mode: on.

Provenance (C2PA)

Crabcrop reads and writes C2PA Content Credentials. The two halves are independently useful: verification reports what a source already carries, and signing attaches credentials to the outputs this server produces.

Verify: in every meta response

Every meta response carries a provenance object; it needs no model, certificate, or opt-in parameter, only meta mode, which is off by default (CRABCROP_META_MODE=1; see Meta endpoint). It reports whether output signing is configured on this server, plus a summary of the manifest store the source carried and the one the output carries: for each, the validation state (valid or invalid), the signer as a validator would show it, and the counts of manifests and ingredients in the store. Verification runs on the c2pa-rs 0.91 line, the first that enforces the specification's exclusion rules. It checks signatures and hashes, not trust lists: crabcrop loads no trust anchors, so valid means the manifest is intact and signed by the certificate it names, whoever issued that certificate, and meta never reports a manifest as trusted. Reading a manifest store is local work, for meta and for signing alike: it makes no network request. The CAWG identity assertions a store may carry are checked against the claim's hashes like any other assertion, but the identity credential inside one is not evaluated, so the state describes the manifest's own signature and hashes, not who the identity names.

{
  "provenance": {
    "signing_configured": true,
    "source": { "state": "valid", "signer": "Example Newsroom", "manifests": 1, "ingredients": 2 },
    "output": { "state": "valid", "signer": "Example Newsroom", "manifests": 1, "ingredients": 1 }
  }
}

Each of source and output is null when that asset carries no manifest store.

Sign: your certificate, proven at boot

Set CRABCROP_C2PA_CERT to a PEM certificate chain and CRABCROP_C2PA_KEY to its private key in PKCS#8 PEM form, and still JPEG, PNG, WebP, and AVIF outputs are signed as they are produced. The identity is yours, like the models and the secret: the server holds no certificate of its own. It is proven at boot with a sign-and-verify round trip, so a broken identity (a bare self-signed certificate, a key that does not match, a chain outside the C2PA certificate profile) is a startup error with the reason named, never a first-request surprise. Setting only one of the pair is a startup error too. CRABCROP_C2PA_TSA_URL optionally adds a timestamp authority. Boot asks it once, after the identity's own round trip has passed, and every call to it is bounded (5 seconds to connect, 15 seconds overall), so a stalled authority fails boot or the signed request instead of hanging either. A request whose signing the authority fails (it stalls, refuses the connection, or answers with something that is not a timestamp) answers 503 with the code provenance_unavailable and Retry-After: 30: the output was rendered but cannot be served unsigned, and a retry may find the authority back. The call follows no redirect, so give the authority's final URL.

CRABCROP_C2PA_CERT=/etc/crabcrop/c2pa-chain.pem \
CRABCROP_C2PA_KEY=/etc/crabcrop/c2pa-key.pem \
crabcrop

A manifest cannot survive a transform byte for byte: decoding and re-encoding drop the segments it lives in. So the source itself is recorded in the output's manifest as its parent ingredient, named by its format. When the source carries a manifest store of its own, the ingredient also records how that store validated, as the C2PA status codes of the check (such as claimSignature.validated), without the URLs that name the source's manifest and assertions. Since 0.11.0 the source's store itself is not copied into the output, under either CRABCROP_METADATA policy: its thumbnails, assertions, and size are the source's, not the output's. A verifier therefore shows the parent as an ingredient without a manifest of its own (ingredient.unknownProvenance), next to the status this server recorded, and meta reports manifests: 1 for every signed output. A source store larger than 1 MiB is not parsed or validated, and its ingredient names the format only. Every image source is recorded this way, SVG, TIFF, BMP, ICO, every HEIF brand the server decodes, and JPEG XL in its box container included. Video and PDF sources are the exception: a frame or page render starts a fresh chain with no source ingredient, opening with a c2pa.created action and the IPTC softwareImage source type. Outputs of the AI edits (background removal, studio mode, region removal, upscale, and the class and face edits) record the edit with the IPTC compositeWithTrainedAlgorithmicMedia digital source type. GIF, JPEG XL, video, and animated WebP outputs are served unsigned in this version.

What a credential says

A valid credential proves origin, not untouched pixels. It attests that this server produced the output from the ingredient it names, under the identity that signed it; the manifest itself records that the image was transformed. Whether verifiers call the result trusted depends on your certificate, not on this software, and meta does not answer it: its state reads valid for any intact manifest, your own outputs included. Outside verifiers that check the C2PA trust list show a chain issued by a CA on that list as trusted, while a private CA chain signs and validates and shows as valid but not trusted, with the signer named. Both are useful; pick with your eyes open.

Explain

Every crabcrop URL can explain itself. Take any image URL, put explain/ in front of the signature segment, and the server answers with a report on that URL instead of the image. Browsers get a readable HTML page; send Accept: application/json for the same report as JSON.

curl "http://localhost:3000/explain/<signature>/crop:1200x630:smart/filters:format(avif):quality(auto)/https://example.com/photo.jpg"

The report carries the signature verdict (valid, which key, when the link expires), the source and its probed facts (media kind, pixel dimensions, and the encoded size when the fetch states it), every operation glossed in plain language in order, the referenced presets with their expansions, a forecast, the canonical form that gets cached with its cache group (since 0.11.0 a form longer than 4096 bytes is cached under its SHA-256 digest, so a very long URL still caches and purges), and links back to the image itself and to the debug focal view when the chain contains a crop. The forecast gives the output dimensions when the chain determines them, the output format and where it came from (format_from: operation, default, or source), and the output pixel count against the budget, plus two refusals the image request would answer with 400: zero_side for a zero-pixel side such as 00x100, and over_dimension for a step that works out a size past 16383 px, or a chain that ends past it, as a 16384 px source with no sizing step does. It walks the operations the image request runs, so the server's default operations apply, merged the same way; the operation list stays the URL's own, and the defaults show in the canonical form. Since 0.10.1 it also applies the DPR factor the image request would: a dpr(...) in the operations, or else the request's own DPR or Sec-CH-DPR header (not at all with CRABCROP_CLIENT_HINTS=0), stepped down as the image request steps it. The JSON gives the factor as forecast.dpr, where it came from as dpr_from (operation, default, hint, or none), and the hint the request carried as dpr_hint.

Explain is safe to expose to the same callers who hold signed URLs. The signature, expiry, and the 100-operation cap are checked exactly as the image path checks them, before any source access, so a bad, expired, or over-cap URL costs zero source fetches. The one probe a valid URL pays for reads only the source's head through the loader, stopping as soon as the head identifies the source: no detection, and nothing written to any cache tier. An SVG, AVIF, or HEIC head is read to its end (up to 256 KB) to size it: an SVG is parsed once in the SVG worker, an AVIF's size is read from its container without decoding it, and since 0.11.0 a HEIC is sized once, with a walk of its item graph. That work runs on a blocking thread, at most two at once, and a probe that cannot start within 5 seconds sheds with 503 (server_busy) and Retry-After. The encoded size is reported only when the fetch states it, so a large source can report none. The report contains only facts derivable from the URL and the source: no secrets, no configuration values, no paths or fingerprints.

Purge

Purges always require an HMAC signature made with the secret, even in unsafe mode. The purge signature is the HMAC-SHA256 of the target under a purge subkey derived from your secret, a separate domain from image signatures, so only the secret holder can invalidate and an image signature does not verify as a purge signature. The subkey is the HMAC of the label crabcrop/purge-key under the secret, which is why no signer signs, and the server never serves, an image remainder that begins with the reserved segment crabcrop. Compute it with your client library (purge_signature, purgeSignature) or the CLI.

# Invalidate every stored variant of one result, across this server's cache tiers
curl -X POST "http://localhost:3000/purge/<signature>/300x200/https://example.com/photo.jpg"
# 200, body like: purged 2

# Invalidate every stored result in a cache group (a preset's output set)
curl -X POST "http://localhost:3000/purge-group/<signature>/small"
# 200, body like: purged 3

For /purge, the path is the original request path without its signature. The target is canonicalized the same way entries are keyed, so purging any equivalent spelling of a path (the jpg alias, leading zeros, a preset reference, a root reference) evicts the shared entry, exp: variants included. A bad purge signature is a 403 and removes nothing; purging a path that is not stored answers purged 0.

A purge reaches the receiving server's memory, its disk tier, and the shared bucket when one is configured. With a bucket, the purge writes a tombstone there before it touches any tier, and every replica reads the tombstones at boot and every 5 seconds after: until the purge's bucket scan finishes, and for 15 minutes after, a disk or bucket copy the purge covers that was written before the purge began is a miss, while a copy rendered after it began serves normally. A replica answers no request, /health included, until its first read of the tombstones ends, and each read, at boot and after, ends within 10 seconds, so a slow or hanging bucket holds back a starting replica's first answer by 10 seconds at most. A tombstone a replica has read stays in force when a later read of it fails, but one it has never managed to read does not apply there until a later read succeeds; failed reads count in crabcrop_cache_tier_errors_total (the reads the 10 second deadline cuts off count once together), and each round of reads with a failure logs one line. On a very large bucket the scan finishes in the background and the count reports what the request itself removed. A purge does not reach another replica's memory, nor a disk directory that replica keeps for itself: a replica that already holds the entry can keep serving it until it evicts the entry, so send the purge to each replica when it must take effect everywhere at once.

Groups come from presets: a response belongs to a cache group for each preset its URL referenced, listed in the Cache-Group header (RFC 9875). Group membership accumulates, so a group purge reaches entries first rendered through a plain, preset-free URL. Image responses also carry Cache-Status (RFC 9211), reporting what the server's own caches did: a memory hit, a disk hit, a shared-tier hit, or an origin fetch. A sealed URL's responses carry no Cache-Group, since its preset names are inside the token; its cache entry still joins those groups, so purge-group reaches sealed renders, but a CDN group purge bridged from the header does not, so purge sealed URLs at the CDN by URL.

Upload

Crabcrop is a fetch-only service by design. The upload endpoint is the one deliberate exception, and it is off by default: configure exactly one destination, CRABCROP_UPLOAD_DIR for a local directory or CRABCROP_UPLOAD_BUCKET for an S3 bucket (which must also be in CRABCROP_ALLOWED_BUCKETS, since uploads are served back as s3:// sources). With neither set, every PUT to /upload/... answers 404 with the code uploads_not_configured, whatever its signature, so a client can tell a server with uploads off from a mistyped path. The route takes only PUT: a GET there answers 405 with Allow: PUT, with or without a destination.

curl -X PUT --data-binary @photo.jpg \
  "http://localhost:3000/upload/<signature>/heroes/photo.jpg"

# Or let the CLI sign and upload in one step
crabcrop upload ./photo.jpg heroes/photo.jpg

The signature covers the name exactly as presented, under an upload subkey derived from the secret: only the secret holder can upload, an image or purge signature does not verify here, and unsafe never authorizes an upload. An upload token can carry an expiry (/upload/<signature>/exp:<unix-seconds>/<name>), and a delegated token should: the signature covers the exp: segment along with the name, so the token stops working at that second. The Python and TypeScript libraries mint this form with an expires argument, the Rust crate with upload_signature_with_expiry, and the CLI with --expires <unix-seconds>.

  • The name is /-separated segments of [A-Za-z0-9._-]: no empty, ., or .. segments, nothing starting with a dot, at most 255 bytes.
  • The body must decode as an image this server can serve (the same decode paths and caps a transform uses); anything else is a 415 and is never stored. SVG bodies are stored sanitized, and the name's extension must match the media kind the body validated as (a name with no extension is accepted as is). The validation decode runs under the same process gate as transforms, so a saturated server sheds an upload with a 503 and Retry-After.
  • CRABCROP_UPLOAD_MAX_MB caps one upload; it defaults to the source fetch cap (CRABCROP_SOURCE_MAX_MB, 10 MB by default) and may not pass it, so a stored original is always one the loader will fetch back. An upload body over the cap is a 413. With a bucket destination, writing the upload may take 10 seconds plus one second per MiB of the body, so the bound grows with the cap; one that runs past it answers 502 (upload_store_unavailable). The body is charged as it arrives to the source buffer budget, so a client that stalls mid-body holds only what it sent. A body the server cannot read to its end, because the client aborted it or framed it badly, is a 400 (upload_unreadable) and is never stored.
  • An upload to an existing name is a 409, answered before the body is decoded, and the final write is a conditional create, so the rule holds even against a racing upload of the same new name; set CRABCROP_UPLOAD_ALLOW_OVERWRITE=1 to let a PUT replace it, which also purges every cached derivative of the replaced original. There is no listing and no delete.

The response body is the source reference to embed in transform URLs, followed by a newline. The X-Crabcrop-Source header carries the exact reference, with no newline, so read the header or trim the body, as crabcrop upload does. For a bucket the reference is s3://originals/heroes/photo.jpg, with the CRABCROP_UPLOAD_PREFIX path before the name when one is set. For a local destination it is the object's path under the file:// root: file:///heroes/photo.jpg when the upload directory doubles as the root, or, with CRABCROP_FILE_ROOT=/srv and CRABCROP_UPLOAD_DIR=/srv/originals, file:///originals/heroes/photo.jpg. The uploaded original is transformable the moment the PUT answers. Enabling uploads changes the server from fetch-only to a service that accepts and stores caller-supplied bytes: give the destination a directory or bucket dedicated to uploads.

Framework loaders

Framework integrations sit on the TypeScript builder: a Next.js custom loader for next/image, a Nuxt provider for @nuxt/image, a Hydrogen loader for external (non-Shopify-CDN) images, an Astro image service for astro:assets, and a SvelteKit loader factory for components and load functions. None is published as a package: each is one file in the repo's frameworks/ directory that you copy into your project, next to npm install @crabcrop/url. Take the files and @crabcrop/url from the same release: since 0.10.0 every integration imports MAX_DIMENSION from it, which 0.9.11 does not export. All five share one dimension rule: a fraction rounds to whole pixels, a value that is not a size (0, negative, or not a number) is left out, and a value past MAX_DIMENSION throws, as does a missing base, instead of minting a URL that cannot load. Each takes an optional server-side preset, which its README recommends as the home for the transform policy, and each README says which server mode fits it:

  • Signed, for production. Run the server without CRABCROP_ALLOW_UNSAFE and build the URLs where the secret lives: Server Components and route handlers, route loaders, Nitro server routes, server load functions, or the Astro service, which runs only at build time and on the server. A loader running in the browser cannot sign, and a signed server answers its URLs with 403.
  • Presets-only, with no secret anywhere. CRABCROP_ONLY_PRESETS=1 with CRABCROP_ALLOW_UNSAFE=1 accepts URLs that carry a preset reference alone, and rejects the per-width sizing the loaders append after the preset with 400. It fits a plain <img> whose preset carries the size (card-640 = 640x0/filters:format(webp)), not a loader's srcset.
  • Unsafe alone, for local development only. With CRABCROP_ALLOW_UNSAFE=1 and presets-only off, every loader works as is, but the server then honors any unsigned operation chain on any source it may fetch: the preset constrains nothing, because a client can drop it or append anything after it. That is an open image proxy.

Command line

The crabcrop binary doubles as its own operator CLI. With no arguments it starts the server, which reads its configuration from the environment only. With any argument it runs the CLI instead: the first argument must name a verb (or be --help or --version), which runs, and the process exits. Any other first argument, a flag included (crabcrop --verison, crabcrop --port=8080), exits 1 with unknown verb and the usage on stderr; it never starts the server, so a custom launch that passes the server binary an argument must drop it. Configuration comes from flags over environment variables: --base / --secret / --key-id over CRABCROP_BASE / CRABCROP_SECRET / CRABCROP_SECRET_KEY_ID, with the base defaulting to http://localhost:3000. Flags go after the verb, and an unknown one is an error too. URLs are validated against the server grammar before they are signed, and the signing verbs refuse a remainder that begins with the reserved segment crabcrop; crabcrop --help lists every verb and flag.

export CRABCROP_BASE=http://localhost:3000
export CRABCROP_SECRET=your-secret

# Sign a URL (validated against the server grammar first)
crabcrop sign "300x200/filters:grayscale/https://example.com/photo.jpg"

# Explain a URL segment by segment, verifying its signature
crabcrop explain "http://localhost:3000/<signature>/300x200/filters:grayscale/https://example.com/photo.jpg"

# Fetch the meta JSON (a bare remainder is signed first).
# The server needs meta mode on (CRABCROP_META_MODE=1); it is off by default.
crabcrop meta "300x200/https://example.com/photo.jpg"
crabcrop meta --placeholders --detections "300x200/https://example.com/photo.jpg"

# Purge one URL, or a whole preset group (Cache-Group)
crabcrop purge "300x200/https://example.com/photo.jpg"
crabcrop purge-group thumb

# Seal a remainder into an opaque token URL (with an optional friendly
# name), or recover the remainder a sealed URL carries
crabcrop seal "300x200/https://example.com/photo.jpg" photo.jpg
crabcrop unseal "http://localhost:3000/s1.<token>/photo.jpg"

# Upload an original to the server's upload store; --expires mints a
# token that stops working at that second
crabcrop upload ./photo.jpg heroes/photo.jpg

# Convert a Thumbor URL (re-signed; losses are reported on stderr)
crabcrop convert-thumbor "unsafe/300x200/smart/https://example.com/photo.jpg"

Deployment and CDN

Run crabcrop behind a reverse proxy or CDN in production. The application bounds its own work (the processing, slow-lane, AI, video, and animation gates shed overload with 503) and the source bytes it holds before that work starts (CRABCROP_SOURCE_BUFFER_MAX_MB, shedding with the same 503), and runs at most 128 source host lookups at once, but connection-level protections belong at the edge: request and header timeouts, connection limits, rate limiting, and TLS termination. Restrict /health to your internal network at the proxy: it is unauthenticated. /metrics exposes traffic and error counters and is not open either: it answers 403 until CRABCROP_METRICS_TOKEN is set, and then requires that bearer token, answering 401 to a missing or wrong one.

Two things hold behind every CDN. Error responses carry Cache-Control: no-store, so an edge that follows the origin's headers never serves one request's failure to the URL's other viewers; the CloudFront recipe also turns off CloudFront's own short caching of errors, which does not wait for headers. And the client hint headers (DPR, Sec-CH-DPR, the width hints, and Save-Data) can change a URL's bytes. Fastly keys on Vary and can leave hints on; with hints on, a response a hint applies to is private, which an edge that follows the origin's headers does not store, so requests with hints go to the origin. Responses a CDN stored before an upgrade to 0.11.0 stay until they expire or are purged, so purge the CDN after upgrading.

Result tiers

Results are stored in up to three tiers. The first is an in-memory LRU, per replica, bounded by CRABCROP_CACHE_MAX_MB (256 MB by default). An optional disk tier (CRABCROP_RESULT_STORAGE_DIR, unset by default) sits underneath it and survives restarts on that host, bounded by CRABCROP_RESULT_STORAGE_MAX_MB (512 MB by default). An optional shared tier (CRABCROP_RESULT_BUCKET) sits behind both: one S3 bucket, or an S3-compatible endpoint, that every replica reads and writes, so all replicas serve the same stored results. A render is written through to the bucket in the background, with at most 64 bucket writes in flight per replica; a render that finds all 64 busy is not written through and counts in crabcrop_cache_shared_puts_skipped_total. Purges fan out to the receiving server's three tiers, not to another replica's memory: see Purge.

Both budgets bound memory, not only bodies. Since 0.11.0 a memory entry counts its cache key (held twice), its ETag and cache group names, and a fixed allowance of a few hundred bytes as well as its body, and a disk entry counts the record the tier's in-memory index keeps for it as well as its file. At boot, a disk directory holding more than the budget, as one filled under a larger budget does, has its oldest entries deleted until the rest fit. A cache key whose canonical form is longer than 4096 bytes is stored under a SHA-256 digest of that form, so one long URL no longer makes a key tens of kilobytes long. The disk directory should hold only what the server writes there, regular files: at boot the server skips anything else named like an entry (a FIFO, a socket, a device, a directory, or a symlink) without opening it, and a lookup that finds one treats it as a corrupt entry, a miss.

Requests to the shared tier and to the upload bucket are bounded by the bytes they move, not by the source fetch timeout, and no setting changes the rule. A write may take 10 seconds plus one second per MiB of its body. A read must start to answer within 10 seconds, may not go 10 seconds without a byte, and must end within 10 seconds plus one second per MiB of the length the store declares. Every other request gets 10 seconds. A lookup that runs out is a miss and a write that runs out is dropped, and both count in crabcrop_cache_tier_errors_total. Before 0.10.1 every bucket request had a fixed 10 seconds, so a large upload over a slow link answered 502 while the store kept receiving it.

Shutting down

On SIGTERM or Ctrl-C the server stops accepting connections, lets the requests in flight finish, waits for the background work they left (renders whose client disconnected after the render started, which finish and are stored, then shared-tier write-throughs and purges whose caller disconnected), then exits with status 0. One deadline bounds the drain: CRABCROP_SHUTDOWN_GRACE_SECS, 8 seconds by default, from the signal on. At the deadline, or at a second signal, the process exits with whatever is still running. The server never runs past the grace, so give the platform a stop timeout longer than it: docker stop and Compose allow 10 seconds and Cloud Run 10, fixed; the Helm chart passes its shutdownGraceSeconds value (default 8) to the server and sets terminationGracePeriodSeconds to it plus 5, so set the grace there: the chart refuses CRABCROP_SHUTDOWN_GRACE_SECS in env.

Errors

Error bodies are plain text with a short message. Send Accept: application/json and any failure instead answers with a JSON envelope, {"error":{"code":"invalid_filters","message":"..."}}: the same status and the same message, plus a stable code clients can branch on. Codes are frozen as published. One exception: a sealed request's failures stay the uniform 403, with no envelope and no code, so a lifted token reveals nothing about its payload; an opened token whose payload has expired answers signature_expired, as the plain form does. A 405 for a method the route does not take carries no envelope either: its body is empty. The same header also asks for meta: while meta mode is off (the default), a JSON request that passes the signature, grammar, and expiry checks answers 403 meta_disabled, so a later failure (fetching or rendering the source) reports its own code in the envelope only on a server with meta mode on.

Grammar failures (a 400) carry the parser's names: empty_path, missing_signature, malformed_signature, invalid_size, invalid_crop, invalid_crop_rect, invalid_pad, invalid_expiry, unknown_preset, invalid_preset, unknown_root, invalid_root, presets_only, invalid_filters, missing_source_url, invalid_focal_rect, invalid_focal_point, invalid_maxage, invalid_debug, invalid_curve, invalid_convolution, invalid_noise, invalid_frame, and invalid_page. 502The source could not be fetched (a network error, a host name that does not resolve or resolves to a non-public address, an origin answer other than 2xx or 404, or a non-image Content-Type), is larger than the fetch cap (CRABCROP_SOURCE_MAX_MB, 10 MiB by default), or does not decode, including AVIF sources in builds without AVIF decoding and formats crabcrop does not decode. A watermark that fails to load lands here too, and so does a configured model, video encoder, frame extractor, or PDF renderer that fails, times out, or produces output the server cannot use.
503The server shed the request because a processing, slow-lane, AI, video, or animation gate, the source buffer budget, or the source host lookup slots waited past its timeout; or the C2PA timestamp authority failed while signing the output (provenance_unavailable). The response carries Retry-After.
504The source fetch timed out (CRABCROP_SOURCE_TIMEOUT_SECS, 10 seconds per fetch by default), or processing ran past the processing timeout (CRABCROP_PROCESS_TIMEOUT_SECS, 30 seconds by default, settable from 1 to 600).

For example, a removebg request to a server with no background-removal model returns 501 with the body removebg is not configured on this server. Errors are never cached; only 200 responses are. Since 0.11.0 every error response, on every route, also carries Cache-Control: no-store (the meta_disabled refusal keeps private, no-store), so a CDN in front does not keep one either, and errors for image URLs carry the same Vary as images.

Configuration

All configuration comes from environment variables. Invalid values are startup errors, booleans included: the server refuses to start rather than run with a wrong port, cache budget, or safety flag. Booleans accept 1, true, yes, or on for on and 0, false, no, or off for off, in any case; anything else fails the boot with the variable named. Names follow one pattern: *_MODEL is an AI model artifact, *_FILE is a file read at boot, *_DIR is a directory, and *_MAX_MB is a size budget in megabytes. Every variable, by area; the long descriptions are in docs/configuration.md:

Cache entries in the persistent tiers are authenticated: each stored entry carries an HMAC-SHA256 tag under a key derived from the server secret, verified before the entry is served, so rotating the secret also invalidates the persistent tiers' contents. Cache keys also carry a fingerprint of the configuration that shapes output, printed at startup, so restarting with any of it changed starts a fresh cache epoch. The fingerprint also carries a rendering version, which a release raises when it changes the bytes some existing URLs serve: 0.10.1 moved it from 3 to 4, and 0.11.0 moves it from 4 to 5. So the first start on 0.11.0 begins a new epoch: expect a cold cache after the upgrade, and during a rolling upgrade old and new replicas keep separate entries instead of serving each other's renders. The epoch does not reach a CDN in front of the server, so purge the CDN after upgrading to 0.11.0: it may hold hinted responses served public, Save-Data encodes stored under a URL's plain entry, and signed outputs that carry their source's manifest store. Rotating the secret without breaking URLs already in the wild is a three-step window; the steps are in docs/configuration.md. One diagnostic sits outside the tables: CRABCROP_STUDIO_TIMING, set to any value, prints the elapsed time of each studio(...) stage to stderr, and changes nothing else; leave it unset in production.
