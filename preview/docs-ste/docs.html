Getting started

Crabcrop is a single Rust binary. You install it. You give it a secret. Then you request images with the operations in the URL. Crabcrop makes no thumbnails in advance. There is no build step. The URL is the API.

Install

# Shell installer (macOS and Linux)
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/dayvson/crabcrop/releases/latest/download/crabcrop-installer.sh | sh

# Docker: the base image, and the AI variant
docker pull ghcr.io/dayvson/crabcrop:0.9.5
docker pull ghcr.io/dayvson/crabcrop-ai:0.9.5

The AI variant ships with two models only: background removal (u2netp) and face detection (YuNet). Every other AI feature needs a model that you configure. Without a model, the feature returns 501. See AI operations.

Prebuilt tarballs are on the releases page. The tarballs cover macOS and Linux. They cover x86_64 and arm64.

You can also build from source with cargo run, cargo build, or cargo install crabcrop. A source build needs a C compiler. On x86_64, it also needs nasm. You need Meson and ninja only for the vendored AVIF decode route.

Quickstart

# 1. Start the server with a new secret. Unsafe is for local dev only.
export CRABCROP_SECRET="$(openssl rand -hex 16)"
CRABCROP_ALLOW_UNSAFE=1 crabcrop
# crabcrop listening on port 3000

# 2. Request an image: resize a source photo to 300x200.
curl "http://localhost:3000/unsafe/300x200/https://example.com/photo.jpg" --output photo.jpg

# 3. In production, drop CRABCROP_ALLOW_UNSAFE and sign the URL instead.
#    In a shell with the same CRABCROP_SECRET, crabcrop sign prints the signed URL.
curl "$(crabcrop sign 300x200/https://example.com/photo.jpg)" --output photo.jpg

Every image request has three parts: GET /<signature>/<operations>/<source-url>. The server applies the operations in path order. It caps the output at 16383 px per axis. It caps the output at 100 megapixels in total. A request over either cap fails with 400, before the server allocates anything.

Signing

Take the remainder of the path. The remainder is the operations and the source URL, exactly as they appear, with no leading slash. Compute HMAC-SHA256 over the remainder. Use your CRABCROP_SECRET as the key. Encode the result in hex. Put the result in the first path segment. A request with a bad signature gets 403 and the body bad signature. The literal signature unsafe skips verification only when the server runs with CRABCROP_ALLOW_UNSAFE=1. Keep it off in production.

printf '%s' '300x200/https://example.com/photo.jpg' \
  | openssl dgst -sha256 -hmac 'your-secret'
# SHA2-256(stdin)= 3c1f6c180116661877bd4c85fd201a178087d74c1cc188cc584e819d901308c6
import { buildURL, buildSrcSet, purgeSignature } from "@crabcrop/url";

const url = buildURL({
  base: "https://img.example.com",
  secret: "your-secret",
  operations: "crop:1200x630:smart/filters:format(webp):quality(80)",
  source: "https://example.com/photo.jpg",
});

const srcset = buildSrcSet({ /* same options */ }, [400, 800, 1200]);
from crabcrop_url import build_url, build_srcset, purge_signature

url = build_url(
    base="https://images.example.com",
    secret="your-secret",
    operations="300x200/filters:grayscale",
    source="https://example.com/photo.jpg",
)

srcset = build_srcset(..., widths=[400, 800, 1200])
use crabcrop_url::{build_url, sign};

let signature = sign(secret, "300x200/https://example.com/photo.jpg");
let url = build_url(base, secret,
    "crop:1200x630:smart/filters:format(avif):quality(auto)",
    "https://example.com/photo.jpg")?;

Secret your-secret, remainder 300x200/https://example.com/photo.jpg, gives HMAC-SHA256 3c1f6c180116661877bd4c85fd201a178087d74c1cc188cc584e819d901308c6. Every SDK runs the standard vectors from spec/test-vectors.json as its test suite. So the client and the server cannot drift apart.

Key IDs and rotation

A signature segment can carry a key ID: <key-id>:<tag>. During a rotation window, the server checks two secrets. It checks the current secret (CRABCROP_SECRET). It checks the outgoing secret (CRABCROP_SECRET_PREVIOUS). So URLs that are already public keep working. They keep working until the URLs under the old key age out. An unknown key ID looks the same as a bad signature: 403. The response gives no hint about which key IDs exist. Builders set the key ID with the keyId or key_id option. On the CLI, use crabcrop sign --key-id.

Sealed URLs

Signing proves that a person with the secret made the URL. But signing hides nothing. Anyone can read the operations and the source in the path. A sealed URL encrypts the whole remainder. It puts an opaque token in place of the signature. The token starts with s1.. After it comes base64url text: the nonce, the ciphertext, and the authentication tag. The seal uses AES-256-GCM. The key comes from the same CRABCROP_SECRET. You manage no second secret. Key rotation works the same as for signatures, with key IDs. Make a sealed URL with the CLI (crabcrop seal). Or use the seal builders in the Rust, TypeScript, and Python SDKs. Python sealing needs the crabcrop-url[seal] extra.

The payload is the whole remainder: the operations and the source together. So a sealed URL serves exactly what the plain form serves. The server opens the token. Then it runs the same pipeline. Both forms share one cache entry. They share one ETag. They share one purge target. Any text after the token is a friendly name. The name is cosmetic only. It makes the link read as an image in logs and in page source. The server never parses the name. You can leave the name off. Builders refuse a remainder over 2,048 bytes. The server refuses a token over 4,096 characters.

Every sealed failure returns the same 403 and the same body, bad signature. A malformed token gives this result. A token made under another secret gives this result. A token whose payload does not parse gives this result. You cannot tell the three apart. One case is different. A token that opens but is past its expiry returns signature expired. The plain form does the same. /explain refuses sealed URLs. It does not decrypt them. An endpoint that opens tokens gives a way to read any token. Anyone who copies a token from a public page could read it that way. To debug a sealed link, unseal it on your own machine with your own secret. Use crabcrop unseal, or the unseal builders in the SDKs. Then explain the plain form. The meta response for a sealed request also reports the result only. It never reports the recipe.

Know what sealing does not do. Sealing hides the recipe from people who read the page. These are the visitors and competitors who can see the link. Sealing does not hide the request itself. A CDN or another network intermediary still sees the request pass. TLS gives privacy for the transport. Sealing is not access control. A sealed URL is a bearer URL. Anyone can replay it, exactly as with a signed URL. Access control stays with the source allowlist, with expiry, and with the system in front of the deployment. For most links, the readable form is the better default. It stays the recommendation. Sealing is the opt-in choice. Use it for links that must be public and unreadable at the same time.

URL anatomy and expiry

Click a segment. The strip shows the whole grammar at a glance. First comes one signature. Then come zero or more operation segments. Then comes the source. The source starts at the first segment that is not an operation. The source can contain slashes.

https://img.example.com/////
Signature. Proof the URL came from you. The server recomputes the HMAC-SHA256 over the operations and source exactly as they appear. A match serves the image; a miss gets a 403.

Expiring URLs

Put an exp:<unix-seconds> segment anywhere among the operations. The segment is inside the signed remainder, so the HMAC covers it. If you extend the expiry without the secret, the signature breaks. The URL is valid only before its exp second. The server allows no clock skew. After that second, the request gets 403 with the body signature expired. Expired URLs never come from the cache. A URL without exp: never expires.

/<signature>/exp:1893456000/300x200/https://example.com/photo.jpg

Per-request cache lifetime

Image responses normally carry Cache-Control: public, max-age=31536000, immutable. The bytes of a signed URL never change. A maxage:<seconds> segment (0 to 31536000) changes the max-age for that response only. It changes the header. It never changes the cache key. So URLs that differ only in maxage share one stored image. maxage:0 drops immutable. Then caches must revalidate. Every response that can be cached carries a strong ETag. So revalidation can return 304 Not Modified.

Each position in the path takes one sizing move. The server applies the moves in order. Try the builder. It assembles the operation exactly as the server parses it.

Fit inside a box

fit-in:<width>x<height>[:adaptive] scales the image in proportion. The image fits inside the box. A 0 axis has no limit. You cannot use flips here. With :adaptive, the box axes swap. They swap when the source orientation differs from the box orientation. So a portrait photo in a landscape box does not get squeezed by the tighter axis.

Pad to an exact size

pad:<width>x<height>[:<fill>] fits the image inside the box. It centers the image. It fills the rest of the canvas. So the output has exactly the size you requested. The fill is a 6-digit hex color. Or use blur. It makes ambient bars from a copy of the image itself. The copy is scaled to cover and blurred heavily. You must give both dimensions. The server rejects a 0 axis, orig, and flips.

Crop to an aspect ratio

crop:<width>x<height>[:<align>] crops the image to the width:height ratio. Then it resizes the image to exactly that size. The align value picks what stays. Use center (the default), top, bottom, left, or right. Or use one of the four corners. Each corner keeps its own edges on the axis that is cut. Or use smart. It puts a window on the focal point. The focal point is a detected face when a face model is configured. Without a face, it is the point with the most local detail. The window moves to keep detected faces whole. Or use face. It puts a window around the largest detected face. facepad pads the window. With no face found, it falls back to the smart window.

Crop a rectangle, focal rectangle, focal point, debug view

crop-rect:<left>x<top>:<right>x<bottom> cuts the exact rectangle of pixels between two corners. A rectangle outside the source image fails with 400. The server does not clamp it. A focal: segment has the same form. It names the rectangle that the next crop: must keep. Center and smart crops put their window on that rectangle. A smart crop with a focal rectangle already set skips detection completely. A focalpoint: segment names a point instead. The next crop: centers on that point. You give the point as fractions of the image dimensions. You can add a zoom: focalpoint:<x>x<y>[:<zoom>]. So focalpoint:0.75x0.4:2 means three quarters across and two fifths down, at zoom 2. Center and smart crops position on the point. The directional alignments and face ignore the point. A URL can carry both focal forms. Then the last form before the crop wins. At zoom 1, the crop is the normal fill crop on the point. Above zoom 1, the window gets tighter around the point. Below zoom 1, the window gets looser. It moves toward the fill window. It can never go past the fill window. The zoom runs from above 0 to 100. The default is 1. The point is a fraction, so it always lands inside the image. It points into the image in effect at that place in the chain. It can never fall outside. So this form has no bounds failure. This is the form that imgix focal-point crops migrate to: fp-x, fp-y, and fp-z. The fractions and the zoom carry over as written. Coordinates name source pixels. dpr does not scale them. debug:focal makes a diagnostic image instead of the result. The image shows the chosen focal point, the face boxes, and the crop window. The server never caches debug responses.

curl "http://localhost:3000/unsafe/crop:1200x630:top/https://example.com/photo.jpg"
curl "http://localhost:3000/unsafe/crop-rect:100x50:700x450/https://example.com/photo.jpg"
curl "http://localhost:3000/unsafe/focal:100x50:700x450/crop:800x600:smart/https://example.com/photo.jpg"
curl "http://localhost:3000/unsafe/focalpoint:0.75x0.4:2/crop:800x600/https://example.com/photo.jpg"

Overlays and text

Three filters composite one image onto another. The server fetches overlay images with the same loader as source images. The same limits and the same source policy apply. If an overlay fails, the request fails with 502. The server does not skip the overlay. These filters run on the pixels of the server. They run at the position of the filter in the chain. So no honest browser preview exists. The examples below are the exact requests.

Watermark

filters:watermark(<url>,<x>,<y>,<alpha>). The URL is percent-encoded. It sits inside a path segment. Negative x and y values anchor from the right edge and the bottom edge. Alpha runs from 0 (invisible) to 100 (opaque). The watermark's own alpha also applies.

# Overlay a logo at the bottom right, 80% opaque
curl "http://localhost:3000/unsafe/filters:watermark(https%3A%2F%2Fcdn.example.com%2Flogo.png,-10,-10,80)/https://example.com/photo.jpg"

Overlay with blend modes

filters:overlay(<url>,<x>,<y>,<alpha>,<blend>[,<width>]) extends the watermark. The blend is normal, multiply, screen, or overlay. These are the CSS formulas, per channel. The optional width scales the overlay first. It scales the overlay to that percent of the width of the base image. Then the server composites the overlay. The server preserves the alpha channel of the base image.

curl "http://localhost:3000/unsafe/filters:overlay(https%3A%2F%2Fcdn.example.com%2Ftexture.png,0,0,60,multiply,100)/https://example.com/photo.jpg"

Text

filters:text(<text>,<size>,<color>,<anchor>) draws a label. It uses a font that you configure on the server (CRABCROP_FONT_PATH). With no font configured, text requests fail with 501. The size is 1 to 1000 px. The color is rrggbb or rrggbbaa. The anchor is one of nine grid points. The points run from top-left to bottom-right. Put text after your resize. Then the text draws sharp at the final size.

curl "http://localhost:3000/unsafe/800x600/filters:text(Sale%20ends%20soon,32,ffffff,bottom-right)/https://example.com/photo.jpg"

Encoding directives do not change the pixels. They steer the encoder. Build one:

quality(auto), verified

quality(auto) picks a quality for each image. The quality runs from 50 for flat images to 95 for detailed images. For JPEG and JPEG XL, crabcrop then checks the pick. It encodes the image. It decodes the result. It scores the result against the processed source with SSIMULACRA2. It adjusts the quality until the score hits the target. The target is 75 by default. It reports the score in meta. When crabcrop picks the quality, the response carries an X-Crabcrop-Quality header. The header gives the value that crabcrop used.

Negotiation

When the URL names no format(...), the Accept header of the request decides the format. AVIF, JPEG XL, and WebP can win. The format with the highest q-value wins. If two formats tie, the server prefers them in that order. The server never picks a format that the client refuses with q=0. A wildcard does not count as an offer. If the client offers none of the three, the server keeps the source format. An animated source never negotiates to JPEG XL. JPEG XL would drop the frames of the animation.

Client hints and Save-Data

When a URL sets no size itself, the server honors width client hints. The hints are Sec-CH-Width, Width, and the viewport variants. The server rounds the width up to a multiple of 100 px. So nearby viewports share one cache entry. A request with Save-Data: on gets the default quality one step lower. The quality drops from 80 to 70. This applies to the formats that carry a quality. A URL that sets quality(...) itself is not affected.

Video output

An animated GIF or WebP can also leave as real video: filters:format(mp4) or format(webm). This is the gifv pattern. Crabcrop ships no codec. An external program does the encode. You configure the program with CRABCROP_VIDEO_ENCODER. FFmpeg is the reference program. The server checks the program at startup. If the variable is not set, video URLs return 501. A failed encode is an error. The server never falls back to the GIF in silence. At most two encodes run at one time. Each encode has a hard timeout and an output cap.

Video frames

A video source can also be an image source. A frame: segment selects one frame. That frame becomes the source image for the rest of the URL. The frame goes through crops, filters, studio mode, and format negotiation. It goes through them like any other source image. Face-safe smart crops are included. The selection applies at decode. It applies wherever the segment sits in the path. A URL can carry several frame: segments. Then the last one wins.

frame:poster
frame:<seconds>
frame:<percent>%
curl "http://localhost:3000/unsafe/frame:50%/800x450/filters:format(webp)/https://example.com/clip.mp4"

frame:poster is the first frame of the video. frame:1.5 is the frame at a timestamp in seconds. frame:50% is the frame at a percentage of the duration. The edges:

  • You can select frames from video only. A frame: segment on a still image fails with 502. It also fails on an animated GIF or WebP source. It fails the way a bad source fails. Animated sources keep their current behavior when no frame: segment is present.
  • A selection out of range clamps. A timestamp past the end of the video gives the last frame. frame:100% gives the last frame too. No part of the request is an error. A percentage needs the duration of the video. If the container reports no duration, the percentage form fails with 400.
  • A malformed selector fails with 400 and the invalid_frame code. A sign, an exponent, a percentage over 100, or a timestamp over 86400 makes a selector malformed. The failure happens before any fetch.

Frame extraction is a feature for the operator. Crabcrop ships no video decoder. The extraction runs in an external decoder. You configure the decoder with CRABCROP_VIDEO_DECODER. FFmpeg is the reference decoder. The server checks the decoder at startup. With the variable not set, a frame: URL returns 501. The server extracts a frame one time for each unique URL, on a cache miss. The result caches and purges like any other result. The meta response for a frame result carries a video object. The object gives the width and height of the stream. It gives the duration in seconds, when the container reports one. It gives the frame_timestamp of the selected frame, after clamping. See Meta endpoint.

PDF pages

A PDF source can also be an image source. A page: segment selects one page. The server renders that page as the source image for the rest of the URL. page:1 is the first page of the document. The server renders the page at a fixed scale of 2. That is a 144 dpi raster. From there, the request is a normal image request. Crops, filters, studio mode, and format negotiation apply without change. One request selects one page. The server has no ranges and no contact sheets. A URL can carry several page: segments. Then the last one wins.

page:<n>
curl "http://localhost:3000/unsafe/page:2/800x1000/filters:format(webp)/https://example.com/report.pdf"

The edges:

  • You can select pages from a PDF only. A page: segment on an image, a video, or any other source fails with 502. It fails the way a bad source fails.
  • Pages are 1-based. The number is exact. page:9 on a document with three pages fails with 400. The server never clamps the number to the last page. This is a deliberate difference from frame: timestamps. A frame is a position inside a stream. A page is a numbered object. The caller picks a page by its number. So a wrong number is a wrong request. It is not a position past the end.
  • The server puts the number in standard form. page:007 is page:7. Both spellings share one cache entry. A malformed selector fails with 400 and the invalid_page code. Zero, a sign, letters, or more than six digits make a selector malformed. The failure happens before any fetch.
  • A document that needs a password fails with 400. A document that is only permission-encrypted opens without a password. It renders normally. The server refuses documents with over 1000 pages.

Page rendering is a feature for the operator. Crabcrop ships no PDF renderer. The rendering runs in an external renderer. You configure the renderer with CRABCROP_PDF_RENDERER. pdftocairo from Poppler is the reference renderer. The server checks the renderer at startup. Crabcrop derives the pdfinfo program from this path. The program sits next to the renderer, in the same directory. Crabcrop uses it to probe documents. CRABCROP_PDF_TIMEOUT_SECS bounds each run. The default is 30. With the variable not set, a page: URL returns 501. The tools get only the document bytes, over stdin. So external references, embedded files, and document actions or scripts have no target. They have no effect. The meta response for a page result carries a pdf object. The object gives the pages count of the document. It gives the page that the server rendered. It gives the page_width and page_height in points. See Meta endpoint.

AI operations

AI filters run ONNX models. You supply the models as files. The server loads the models at boot, before it reports ready. Crabcrop never downloads a model. If a configured model cannot load, the server fails at startup. The failure is not a surprise for the first request. With no model configured, the filter returns a clean 501. Nothing degrades in silence. upscale never falls back to a plain resize. A detection failure fails a redaction request. The server never serves an unredacted image by mistake. Fetch and decode limits

  • 10 seconds per HTTP request; each redirect hop (up to 5) gets its own 10 second budget.
  • 10 MiB maximum body; larger sources fail with 502.
  • A Content-Type header, when present, must start with image/. Two cases are exceptions. The first case is a video/* source under a frame: segment (see Video frames). The second case is an application/pdf source under a page: segment (see PDF pages).

What a credential says

A valid credential proves origin. It does not prove untouched pixels. It attests one fact. This server produced the output from the ingredient that it names. Explain

Every crabcrop URL can explain itself. Take any image URL. Put explain/ in front of the signature segment. The server returns a report on that URL. It does not return the image. Browsers get a readable HTML page. Send Accept: application/json to get the same report as JSON.

curl "http://localhost:3000/explain/<signature>/crop:1200x630:smart/filters:format(avif):quality(auto)/https://example.com/photo.jpg"

The report has several parts. It has the verdict on the signature: valid or not, which key, and when the link expires. It has the source and the facts from the probe: the media kind, the pixel dimensions, and the encoded size. It has every operation, in order, each with a plain-language gloss. It has the presets in the URL, with their expansions. It has a forecast. The forecast gives the output dimensions when the chain fixes them. It gives the output format. It gives the output pixel count against the budget. It has the standard form that the server caches, with its cache group. It has links back to the image itself.

You can expose explain to the same callers that hold signed URLs. It is safe. The server checks the signature and the expiry first. It checks them exactly as the image path checks them. It checks them before any access to the source. So a bad or expired URL costs zero fetches of the source. A valid URL pays for one probe only. The probe is a single fetch with a bound. Its facts come from headers alone. The probe does no decode. It runs no detection. It writes nothing to any cache tier. The report has only facts from the URL and the source. It has no secrets. It has no configuration values. It has no paths and no fingerprints.

Purge

A purge always needs an HMAC signature made with the secret. This is true in unsafe mode too. The purge signature is the HMAC-SHA256 of the target. The server computes it under a purge subkey. The subkey comes from your secret. The subkey is a separate domain from image signatures. So only the holder of the secret can invalidate a result. And no one can replay an image signature as a purge. Compute the signature with your client library (purge_signature, purgeSignature). Or compute it with the CLI.

# Invalidate every stored variant of one result, across all cache tiers
curl -X POST "http://localhost:3000/purge/<signature>/300x200/https://example.com/photo.jpg"
# 200, body like: purged 2

# Invalidate every stored result in a cache group (a preset's output set)
curl -X POST "http://localhost:3000/purge-group/<signature>/small"
# 200, body like: purged 3

For /purge, the path is the original request path. The path has no signature. The server puts the target in standard form. It uses the same form as the cache keys. So a purge of any equal spelling removes the shared entry. The spellings include the jpg alias, leading zeros, a preset reference, and a root reference. exp: variants are included. A bad purge signature gives a 403. It removes nothing. A purge of a path that is not stored returns purged 0.

Groups come from presets. A response belongs to a cache group for each preset in its URL. The Cache-Group header lists the groups (RFC 9875). Group membership adds up over time. So a group purge reaches entries that first came from a plain URL with no preset. Image responses also carry Cache-Status (RFC 9211). The header reports what the caches of the server did. The result is a memory hit, a disk hit, a shared-tier hit, or a fetch from the origin.

Upload

Crabcrop is a fetch-only service by design. The upload endpoint is the one deliberate exception. It is off by default. Configure exactly one destination. Use CRABCROP_UPLOAD_DIR for a local directory. Or use CRABCROP_UPLOAD_BUCKET for an S3 bucket. With neither variable set, the endpoint does not exist. Then a PUT is a plain 404.

curl -X PUT --data-binary @photo.jpg \
  "http://localhost:3000/upload/<signature>/heroes/photo.jpg"

# Or let the CLI sign and upload in one step
crabcrop upload ./photo.jpg heroes/photo.jpg

The signature covers the name, exactly as you present it. The server uses an upload subkey for it. The subkey comes from the secret. So only the holder of the secret can upload. No one can replay an image signature here. No one can replay a purge signature here. And unsafe never authorizes an upload. An upload token can carry an expiry (/upload/<signature>/exp:<unix-seconds>/<name>). Give a delegated token one. The signature covers the exp: segment and the name. So the token stops at that second.

  • The name has segments. / separates the segments. Each segment uses [A-Za-z0-9._-] characters. No segment can be empty. No segment can be . or ... No segment can start with a dot. The name has at most 255 bytes.
  • The body must decode as an image that this server can serve. Any other body gives a 415. The server never stores it. The server stores SVG bodies in sanitized form. The extension of the name must match the media kind of the body, as the check finds it.
  • CRABCROP_UPLOAD_MAX_MB sets the cap for one upload. The default is 10 MB. An upload body over the cap gives a 413.
  • An upload to a name that exists gives a 409. Set CRABCROP_UPLOAD_ALLOW_OVERWRITE=1 to let a PUT replace the file. A replace also purges every cached derivative of the old original. The endpoint has no list function. The endpoint has no delete function.

The response body is the exact source reference for transform URLs. For a local destination, the reference is file:///heroes/photo.jpg. For a bucket, it is s3://originals/heroes/photo.jpg. The server also returns the reference in the X-Crabcrop-Source header. You can transform the uploaded original at once. It works from the moment the PUT returns. Uploads change the server. The server stops being fetch-only. It accepts bytes from callers and stores them. Give the destination a directory or a bucket for uploads only.

Deployment and CDN

Run crabcrop behind a reverse proxy or a CDN in production. The application bounds its own work. The processing, AI, video, and animation gates shed overload with 503. Result tiers

The server stores results in up to three tiers. The first tier is an LRU in memory. It is per replica. CRABCROP_CACHE_MAX_MB bounds it. The default is 256 MB. An optional disk tier sits under the first tier. You set it with CRABCROP_RESULT_STORAGE_DIR. It is not set by default. It survives restarts on that host. CRABCROP_RESULT_STORAGE_MAX_MB bounds it. The default is 512 MB. An optional shared tier sits behind both tiers. You set it with CRABCROP_RESULT_BUCKET. It is one S3 bucket, or an S3-compatible endpoint. Every replica reads it and writes it. So all replicas serve the same stored results. A purge reaches all three tiers.

Errors

Error bodies are plain text with a short message. Send Accept: application/json with a grammar failure, and the server returns a JSON envelope instead: {"error":{"code":"invalid_filters","message":"..."}}. That failure gives a 400. The codes are the stable names of the parser. The names are frozen as published. The codes are invalid_size, invalid_crop, invalid_filters, unknown_preset, unknown_root, invalid_root, invalid_frame, invalid_page, invalid_focal_point, and the rest.

StatusMeaning
400The path or the operations do not parse. Or the operation is not supported. Cases include a malformed segment and an unknown filter. Cases include removebg into a format without alpha. Cases include upscale past its caps. Cases include a crop-rect outside the image. Cases include a video format on a still source.
401A /metrics request with a bearer token that is missing or wrong. This applies when CRABCROP_METRICS_TOKEN is set.
403Bad signature, an expired exp: URL, or the source refused by the source policy.
404A PUT to /upload/... when uploads are not configured, or a PUT to any path that is not the upload route.
413An upload body larger than the CRABCROP_UPLOAD_MAX_MB cap.
415An upload body that does not decode as an image that this server can serve. The server never stores it.
409An upload to an existing name, with overwrite off.
500The encode of the output failed. Or an AI model failed at inference time. A model that cannot load at all fails at startup instead.
501The URL is valid. But this server has no configuration for it. Cases: an AI filter with no model, a text overlay with no font, a video format with no encoder.
502The server cannot fetch or decode the source. Or the source is larger than the fetch limit of 10 MiB. Or a watermark fails to load. Or a configured encoder or model makes output that the server cannot use.
503The server shed the request. A gate waited past its timeout. The gate is a processing, AI, video, or animation gate. The response carries Retry-After.
504The fetch of the source ran past its timeout. The timeout is 10 seconds per request. Or processing ran past the processing timeout. You set the timeout with CRABCROP_PROCESS_TIMEOUT_SECS. The default is 30 seconds. You can set it from 1 to 600.

For example, a removebg request to a server with no background removal model returns 501. The body is removebg is not configured on this server. The server never caches errors. It caches only 200 responses.
